## 任务一：微调 BERT 做断句标点

**建模方式：逐字序列标注。**给每个字一个标签，表示这个字**后面**跟什么标点：
```
原文：學而時習之，不亦說乎？
字：  學 而 時 習 之 不 亦 說 乎
标签：O  O  O  O  ， O  O  O  ？
```
- 标签共 8 种：`O ， 。 、 ： ； ？ ！`。引号、书名号、括号不参与断句，预处理时去掉。
- 模型：`BertForTokenClassification` = 预训练 BERT + 一个新的 8 分类线性层，整体微调。
- 每个字直接作为一个 token 查词表（`convert_tokens_to_ids`），不用 BERT 自带的分词，保证字和标签一一对应。
- 训练、测试**按篇划分**（每 10 篇取 1 篇测试），避免同一篇文章既在训练集又在测试集。
- 评价：**断句 F1**（该断的地方断了没有）和**标点 F1**（断的位置和标点种类都要对）。

## 任务二：长文的 Batch 解码设计

BERT 一次最多 512 token，长文必须切成窗口。`punctuate_long.py` 比较三种做法：

| 方法 | 做法 | 能否批处理 |
|---|---|---|
| **A 课件基础法** | 取 400 字预测，在前 300 字里找最后一个 `。？！`，采纳它之前的结果，下一窗从它后面开始 | 不能：下一窗的起点取决于上一窗的预测，只能一窗一窗串行 |
| **B 基础法 + 多篇并行** | 同 A，但同时处理 batch 篇文章，每步把各篇“当前窗口”拼成一个 batch | 部分可以：篇与篇之间并行，篇内仍串行。一篇特别长时，后期 batch 会凑不满 |
| **C 重叠滑窗 + 全量批处理** | 窗口位置**事先固定**：400 字一窗，步长 300，相邻窗口重叠 100 字。每个窗口只采纳中间那段（左右各留 50 字上下文），首尾窗口负责到文本两端 | 完全可以：所有窗口互不依赖，所有文章的所有窗口按长度排序后一次性打包 |

方法 C 的关键是**去掉窗口之间的依赖**：A 用“句号后重启”来保证窗口边界附近的字有上下文，C 改用“固定重叠 + 只采纳中间段”达到同样目的。这样窗口就能任意并行，batch 开多大只受显存限制。另外两个小优化：
- **按长度排序再分 batch**：同一 batch 内长度接近，padding 少。
- **推理用半精度**（`model.half()` + autocast），在 GPU 上更快、更省显存。

用标准答案模拟器自检时（测试集 24 篇、13499 字，其中 8 篇超过 512 字），三种方法需要的前向次数：

| 方法 | 前向次数（batch=8） |
|---|---|
| A 课件基础法 batch=1 | 53 |
| B 基础法 + 多篇并行 | 13 |
| C 重叠滑窗批处理 | **7** |

真实耗时还取决于每次前向的 batch 大小。在 GPU 上，batch 从 1 增加到 16，单次前向的时间增加不多，所以前向次数基本决定了总耗时。

**可以观察的点**
- 断句 F1 通常明显高于标点 F1：判断“哪里该断”比判断“用逗号还是句号”容易，后者常常本身就有多种合理选择。
- 比较 A 和 C 的 F1：如果几乎相同、而 C 快很多，说明“固定重叠”替代“句号后重启”没有损失质量。
- `bert-base-chinese` 是用现代中文预训练的，对古文并不最合适。可以试试 `--model SIKU-BERT/sikubert`（用《四库全书》繁体古文预训练）做对照，其他条件不变，看 F1 是否提高。
