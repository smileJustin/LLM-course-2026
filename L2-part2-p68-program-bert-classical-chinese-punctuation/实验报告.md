## 一、实验目的
课件明确说明这道题不是从头训练 BERT，而是**微调应用**：
- **任务一（基础）**：在已经训练好的 BERT 上，用现成语料微调，得到一个断句标点模型；
- **任务二（工程）**：BERT 最多只能看 512 个 token，古文一段可能有几千字，只能滑窗处理。课件给出的基础方法是“每次 400 字，只取前约 300 字的结果，在某个句号后结束作为新的起点”，但效率很低。要求设计利用 Batch 解码的高效方案；
- 完成完整的训练和测试流程。

## 二、实验环境与数据
| 项目 | 说明 |
|---|---|
| 环境 | Windows，Python 3.10，PyTorch，transformers；**只用 CPU**（没有使用 GPU） |
| 预训练模型 | `bert-base-chinese`（12 层，隐藏维度 768，约 1 亿参数） |
| 语料 | 《古文观止》222 篇 + 《孟子》14 章 + 《大学》《中庸》，共 238 篇、约 19 万字，繁体，带标点。来自 GitHub 开源项目 chinese-poetry |
| 划分 | **按篇划分**：每 10 篇取 1 篇做测试（24 篇、13,499 字），其余 214 篇训练，避免同一篇文章既在训练集又在测试集 |

**关于语料的选择**：课件提到“古文句读拿现代文做训练和测试就足够了，比如人民日报 9801”。本实验选择直接使用古文语料，理由是题目要解决的是古文断句，用古文训练和测试，评估结果更直接反映目标任务的效果。代价是古文语料规模较小（19 万字），且 `bert-base-chinese` 是用现代中文预训练的，存在领域差异（见第六节）。

## 三、任务一：微调 BERT 做断句标点

### 1. 问题建模：逐字序列标注
给每个字一个标签，表示这个字**后面**跟什么标点：
```
原文：學而時習之，不亦說乎？
字：  學 而 時 習 之 不 亦 說 乎
标签：O  O  O  O  ， O  O  O  ？
```
- 标签共 8 种：`O ， 。 、 ： ； ？ ！`。O 表示后面没有标点。
- 引号、书名号、括号不参与断句，预处理时去掉；半角标点统一成全角；连续两个标点只保留第一个。
- 这样，断句标点就变成了一个标准的 token 分类问题，可以直接用 `BertForTokenClassification`。

### 2. 模型与训练设置
- **模型**：`BertForTokenClassification` = 预训练 BERT 主体 + 新加的线性分类层（768 → 8）。
  加载时 transformers 报告：预训练时的 MLM 输出头（`cls.predictions.*`）、下一句预测头（`cls.seq_relationship.*`）和 `pooler` 在本任务中用不到，被丢弃（UNEXPECTED）；新的 `classifier.weight/bias` 随机初始化（MISSING）。这正是微调的标准形态。
- **输入**：每个字直接作为一个 token 查词表（`convert_tokens_to_ids`），不用 BERT 的 WordPiece 分词，保证字和标签一一对应。训练时把每篇切成不超过 256 字的段，共 659 段。
- **词表覆盖**：训练集中有 1,688 个字不在 `bert-base-chinese` 的词表里，会变成 `[UNK]`，约占训练集字数的 1.2%，多是古文生僻字和异体字。
- **超参数**：

| 参数 | 取值 | 说明 |
|---|---|---|
| 优化器 | AdamW，weight_decay=0.01 | BERT 微调的标准选择 |
| 学习率 | 3e-5，前 10% 步线性预热，之后线性衰减 | BERT 论文推荐的微调学习率范围是 2e-5 ~ 5e-5 |
| batch size | 16 | |
| 轮数 | 3 | |
| 梯度裁剪 | 1.0 | 防止训练初期梯度过大 |

- **评价指标**：
  - **断句 F1**：只看“该不该断”，即预测和真实标签是否都不是 O；
  - **标点 F1**：断的位置对、标点种类也要对。

### 3. 训练结果
| 轮次 | 训练损失 | 断句 F1 | 标点 F1 | 用时（CPU） |
|---|---|---|---|---|
| 微调前（分类层随机） | – | 0.304 | 0.035 | – |
| 第 1 轮 | 0.736 | 0.739 | 0.507 | 445 s |
| 第 2 轮 | 0.369 | 0.793 | 0.596 | 461 s |
| 第 3 轮 | 0.313 | **0.800** | **0.612** | 398 s |

训练总用时约 22 分钟。

### 4. 结果分析
1. **微调收效很快**：只训练 1 轮，断句 F1 就从 0.30 提高到 0.74。BERT 在预训练中已经学到了大量汉语知识，新加的分类层只需少量数据就能学会利用这些知识，这正是“预训练 + 微调”范式的优势。
2. **第 3 轮基本饱和**：断句 F1 只提高 0.007。训练损失仍在下降，但测试集收益已经很小，再训练下去容易过拟合，3 轮是合适的。
3. **断句 F1 明显高于标点 F1（0.80 对 0.61）**：判断“这里该不该断”比判断“用逗号还是句号”容易得多。古文原本没有标点，现代整理本中逗号、句号、分号的选用本身就有很大主观性，很多“标点错误”其实也说得通。
4. **典型错误**（测试样例）：

| 原文 | 模型输出 | 错误类型 |
|---|---|---|
| 潁考叔，純孝也 | 潁考叔純孝也 | **漏断**：古文短句连写，模型偏保守 |
| 繕甲兵，具卒乘 | 繕甲兵具，卒乘 | **断错位置**：“具”在这里是动词“准备”，模型把它当成了“甲兵具”的一部分。需要古汉语语法知识 |
| 號泣于旻天 | 號泣于旻，天 | **词被切开**：“旻天”是一个词（秋天的天空），属于罕见词，模型不认识，在中间断开了 |
| 其是之謂乎！ | 其是之謂乎？ | **标点种类不同**：“乎”既可表疑问也可表感叹，模型选了更常见的疑问用法，说得通 |

## 四、任务二：长文本的 Batch 解码

### 1. 问题
BERT 一次最多 512 个 token，测试集中有 8 篇超过 512 字，最长的《孟子·萬章上》有 2,675 字，必须切成窗口处理。课件的基础方法是：
> 每次取 400 字预测，在前 300 字里找最后一个句末标点（。？！），采纳它之前的结果，下一个窗口从它后面开始。

这样做的好处是每个窗口都从句子开头开始，窗口边界附近的字有足够的上下文。问题是**下一个窗口从哪里开始，取决于上一个窗口的预测结果**，窗口之间有先后依赖，只能一个一个串行处理，无法批处理。

### 2. 三种解码方法
| 方法 | 做法 | 能否批处理 |
|---|---|---|
| **A 课件基础法** | 如上，一次一个窗口（batch=1） | 不能 |
| **B 基础法 + 多篇并行** | 仍按句号重启，但同时推进多篇文章，每一步把各篇“当前的窗口”拼成一个 batch | 部分可以：篇与篇之间并行，篇内仍串行。长文章到后期只剩自己，batch 凑不满 |
| **C 重叠滑窗 + 全量批处理** | 窗口位置**事先固定**：400 字一窗，步长 300，相邻窗口重叠 100 字。每个窗口只采纳中间 300 字的结果，左右各留 50 字上下文；第一个窗口从 0 开始，最后一个窗口负责到结尾。所有文章的所有窗口按长度排序后打包成 batch | 完全可以：窗口之间没有任何依赖 |

方法 C 的核心思想是**用“固定重叠”代替“句号重启”来保证上下文**：句号重启必须等前一个窗口的结果；固定重叠只需要保证每个字离窗口边缘至少 50 字，窗口位置可以提前全部算好。另外两个细节：
- **按长度排序再分 batch**：同一 batch 里的窗口长度接近，padding（补齐的空位）少，浪费的计算少；
- **半精度推理**：在 GPU 上自动使用 fp16（`model.half()` + autocast），本实验在 CPU 上运行，没有用到。

**正确性验证**：`python common.py` 用“标准答案模拟器”代替 BERT，验证三种方法都能把全文完整、无重叠地拼回去（三种方法的 F1 都是 1.0）。

### 3. 实验结果（CPU）
测试集 24 篇整文、13,499 字，每种 batch 大小单独运行一次：

| batch | 方法 | 前向次数 | 用时 | 断句 F1 | 标点 F1 |
|---|---|---|---|---|---|
| 4 | A 课件基础法（batch=1） | 53 | 12.14 s | 0.800 | 0.609 |
| | B 基础法 + 多篇并行 | 18 | 11.43 s | 0.800 | 0.609 |
| | C 重叠滑窗批处理 | 14 | **8.63 s** | 0.800 | 0.608 |
| 8 | A 课件基础法（batch=1） | 53 | 13.63 s | 0.800 | 0.609 |
| | B 基础法 + 多篇并行 | 13 | 12.65 s | 0.800 | 0.609 |
| | C 重叠滑窗批处理 | 7 | **10.15 s** | 0.800 | 0.608 |
| 16 | A 课件基础法（batch=1） | 53 | 16.33 s | 0.800 | 0.609 |
| | B 基础法 + 多篇并行 | 10 | 13.51 s | 0.800 | 0.609 |
| | C 重叠滑窗批处理 | 4 | **10.88 s** | 0.800 | 0.608 |

同一次运行内，C 相对 A 的加速比：batch 4 时 1.41 倍，batch 8 时 1.34 倍，batch 16 时 1.50 倍。

### 4. 结果分析
1. **质量完全不受影响**：三种方法的断句 F1 都是 0.800，标点 F1 只差 0.001（0.609 对 0.608）。这说明“固定重叠、只采纳中间段”完全可以替代“句号重启”。另外，长文滑窗解码的 F1（0.800 / 0.609）和训练时按 256 字分段评估的结果（0.800 / 0.612）几乎相同，说明滑窗处理本身没有损失精度。
2. **前向调用次数大幅减少**：方法 A 无论如何都要 53 次；方法 B 降到 10~18 次；方法 C 降到 4~14 次，batch 16 时只需 4 次，是方法 A 的 1/13。方法 B 减少得没有 C 多，原因正如设计时预料：最长的几篇文章拖到最后，batch 凑不满。
3. **但在 CPU 上，用时只缩短了约 30%**，远小于前向次数的减少。原因是：
   - 三种方法实际计算的字数差不多，窗口总数都在五十个左右，只是打包方式不同。**CPU 的计算能力是固定的**，一次算 1 个窗口和一次算 16 个窗口，总计算量相同，耗时也基本相同。批处理在 CPU 上只能省去每次调用的固定开销，以及让矩阵乘法稍微高效一点，所以只快了 30% 左右；
   - **GPU 的情况完全不同**：一个 400 字的窗口远远用不满 GPU 的几千个计算核心，batch=1 时大部分核心在空转。把 16 个窗口打包，GPU 用几乎相同的时间同时算完，所以在 GPU 上，前向次数基本决定了总耗时。课件中提到“12G 游戏卡 batch 可以开到 4~9，更好的卡可以开到 16~64”，正是针对这种情况。按前向次数估算，在 GPU 上方法 C 可以比方法 A 快约一个数量级。本实验只有 CPU 环境，**没有在 GPU 上实测验证**。
4. **CPU 上 batch 不是越大越好**：方法 C 在 batch 4、8、16 时的用时分别是 8.63 s、10.15 s、10.88 s，batch 越大反而越慢。原因是 batch 越大，同一个 batch 里长短不一的窗口越多（测试集 24 篇中有 9 篇不足 400 字，长文章的最后一个窗口也往往较短），需要补齐的 padding 越多。CPU 上这些空位要实实在在地计算，GPU 上则基本是并行完成的。需要注意的是，同一个方法 A 三次运行的用时从 12.1 s 波动到 16.3 s，说明电脑当时的负载在变化，**跨运行比较的误差约 ±2 秒**。所以“batch 越大越慢”的趋势只能作为参考，同一次运行内 A、B、C 的对比更可靠。

### 5. 结论
方法 C 把串行依赖去掉之后，窗口可以任意打包，batch 大小只受显存限制。在本实验的 CPU 环境中，它比课件基础法快约 1.3~1.5 倍，而且结果质量完全相同。在 GPU 上，它的优势会大得多，可以充分利用课件中提到的大 batch。

## 五、完整流程与复现
1. `python common.py`：自检三种解码方法的拼接逻辑（几秒钟）。
2. `python train.py`：微调 BERT，模型保存到 `bert_punct_model/`。首次运行会自动下载 `bert-base-chinese`（约 400MB），默认通过国内镜像 hf-mirror.com 下载。训练好的模型约 400MB，已在 `.gitignore` 中排除，不上传 GitHub。
3. `python punctuate_long.py --batch-size 4`（以及 8、16）：长文三种解码方式对比，结果分别写入 `运行结果_punctuate_batch*.txt`。
4. `python punctuate_long.py --file 某篇古文.txt`：给任意古文加标点，结果写到 `某篇古文_标点.txt`。

## 六、局限与可改进之处
1. **没有在 GPU 上验证任务二**：本实验的核心目标是提高 GPU 上的解码效率，但只有 CPU 环境。有 GPU 时重跑 `punctuate_long.py`，就能得到真实的加速比。
2. **预训练模型与古文不匹配**：`bert-base-chinese` 用现代中文预训练，1.2% 的字是 `[UNK]`，对“旻天”这类罕见词和“具”的动词用法理解不足。可以换用古文预训练模型做对照，比如 SikuBERT（用《四库全书》训练）或 GuwenBERT，其他条件保持不变，看 F1 能提高多少。
3. **语料规模小**：只有 19 万字，测试集 24 篇。可以加入《史记》《资治通鉴》等更大的古文语料；也可以按课件的建议，先在人民日报等现代文上训练，再用古文测试，观察跨语体迁移的效果。
4. **评价指标较粗**：标点 F1 对“逗号还是分号”这类可接受的差异一律算错。可以再报告“句末标点（。？！）F1”和“句内标点 F1”，区分严重错误和轻微差异。
5. **长度限制没有用满**：窗口 400 字是沿用课件的设置，BERT 实际可以用到 510 个字。在 GPU 上可以试一试更大的窗口和步长，进一步减少窗口数。
